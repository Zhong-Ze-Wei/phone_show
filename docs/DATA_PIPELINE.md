# 手机数据采集与自动清洗

新采集流程读取品牌官网公开目录和 ZOL 公开 HTML，不依赖旧 MySQL，也不删除旧 Excel、Markdown 或数据库。官方目录先发布，ZOL 的独立新品模块按品牌发现，随后正常完整同步刷新公开列表。采集结果经过页面校验后交给存储自动清洗；不完整详情和失败请求保留到队列，不以零价格、空参数或“成功”代替。

## 使用

```powershell
# 创建新的网络快照，采集公开列表、时间排序列表及其系列版本
uv run phone-assistant sync --force

# 只更新官方目录与各品牌新品模块/对应详情，不重抓旧热门列表
uv run phone-assistant sync --latest

# 接续上一未完成批次，复用该批次已校验的页面和详情
uv run phone-assistant sync --resume

# 查看数据质量（命令由应用入口提供）
uv run phone-assistant quality
```

`--resume` 用于恢复同一个采集批次，已经成功的详情不会重复抓取。要获取之后更新的新资料，应创建新批次。CLI 和网页共享进程锁，已有同步运行时，第二个任务立即报告已有任务，不重复请求源站。

CLI 同步退出码为：0 完整完成，2 有效数据已发布但覆盖仍为 `partial`，1 配置或执行错误。自动化任务可以据此区分完整与部分完成，详细原因以 JSON 报告为准。

Python 接口：

```python
from phone_assistant.pipeline import run_sync
from phone_assistant.storage import Storage

report = run_sync(storage=Storage(), force=True, progress=print)
```

可选参数有 `resume`、`force`、`delay`、`list_url`、`seed_urls`、`data_dir`、`limit`、`variants_only`、`latest_only`、`include_official`。`latest_only=True` 对应 CLI `--latest`，不会刷新旧热门列表，不能宣称旧机型价格也已更新。`variants_only=True` 仅从既有批次已保存的系列页发现额外版本入口，补齐对应页面，不重跑列表或重试已拦截列表。默认 ZOL 限速不低于每次请求间隔 0.8 秒；`limit` 只供检查，使用后报告明确标记未完成覆盖。

## 页面发现与校验

默认从正常公开网格页 `https://detail.zol.com.cn/cell_phone_index/subcate57_list_1.html` 开始，源页面“手机品牌报价大全”和普通品牌目录 `/category/57.html` 动态提供品牌页面，不硬编码产品型号或品牌 ID。按品牌读取标题明确为“手机新品”的独立模块，忽略广告、猜你喜欢与热门排行。优先采集 vivo、华为、荣耀、OPPO、苹果，再按实际目录覆盖其他品牌。网页上的“时间”排序属于额外列表来源，不能作为新品完整性的证明。

2026-10-04 实测 vivo 主列表有 29 条、“时间”排序列表有 25 条，均没有 X500；同一品牌页新品模块实际列出 10 个 X500 SKU。这是此前新品漏采的根因：旧流程只发现主列表，已经发现的 715 条详情全部完成不等于各品牌新机已经发现。

全量模式也跟随主列表正常分页，列表与网格布局分别解析，不猜测年度筛选或参数地址。新品先取得有效详情并逐条发布，其余普通列表的刷新不阻止它们进入应用。

每个基型读取产品首页提供的参数链接和系列链接。系列页解析所有 `model_page_N` 型号行，同时跟随系列自己的分页链接；不会只解析第一页 CSS 类。系列数量按同系列所有已采页面的独立 ID 聚合后核对，避免把每页行数误当全系列行数。仍有宣传数量与可见成员差异时，报告为 `partial`，不编造未展示的型号。系列行没有参数链接时，读取该型号的真实产品首页发现链接。

系列首页可能只展示四个版本，“共有 N 款产品”普通链接会指向参数对比页。采集跟随这个真实链接，逐型号列读取完整参数、图片、参考价和商家状态，严格核对产品 ID 与每行列宽；空标签行没有真实参数名，忽略该行。每个版本仍要求至少五项有效参数。对比页本身提供完整可核实详情时，以该页作为规格来源，避免构造并不存在的单机参数 URL。

列表必须有可识别条目、产品 ID 和名称；详情必须有正确产品身份及至少五项有效参数。访问验证、短响应、错误页、分页返回另一个页完全相同的产品集合都进入失败队列。对 `service.zol.com.cn/checking` 验证页面停止该 URL，不执行挑战脚本、不构造验证 cookie、不换代理规避验证。

源站的不同 URL 或不同时点可能给出不同总数。报告记录每页实际条目、声明总数、独立 ID 数量和 `list_count_mismatch`，不能把某次首页的 207 款、5 页当成长期固定事实。只有采集事实支持的范围才可宣称已覆盖。

## 价格、在售与来源

- `price` 保留源站参考价原文；没有参考价时保持未知，不从模型记忆补价格。
- 参数页的“电商报价”单独保留在原始参数中，不替代参考价，也不宣称已经验证库存。
- `listed` 表示当前公开列表出现，或系列明确显示在售电商；价格或系列行明确停产时优先标记 `historical`，其他系列成员保持 `unknown`。
- 上市年份与抓取时间是两种不同事实。今天重新采集的 2021 年手机仍是旧机型。
- `source_url` 指向产品页面；`price_source_url` 和 `specs_source_url` 分别记录参考价和规格的真实来源。
- `new_from_source`、`new_release_catalog_url`、`source_position` 指明具体新品模块证据；`catalog_fetched_at`、`discovered_at` 使用该目录的真实响应时间，与规格响应时间分别保存。系列版本继承所属新品的目录证据。
- “即将上市”“价格面议”等状态不覆盖另一已采来源的同 SKU 确定报价；没有同 SKU 证据时价格仍未知。官网“起价”不能充当任意容量 SKU 的确定报价。

交给清洗层的原始字段：`id`、`name`、`brand`、`price`、`image_url`、`source_url`、`fetched_at`、`availability`、`specs`、`origin`。`specs` 是详细参数页中文参数名到原文的平面映射。`fetched_at` 与 `specs_fetched_at` 使用详细参数响应的实际 UTC ISO 时间，`price_fetched_at` 使用报价所在列表、系列或产品首页响应的实际时间。恢复缓存不会把旧响应日期改为今天；旧缓存缺少元数据时，时间保持未知。旧 Excel 导入不伪造抓取时间。

发现早期错误的来源时间时，可调用 `repair_cached_provenance(storage=Storage())`，仅使用已保存的 HTML 和响应元数据离线纠正。纠正记录追加到原始记录和存储快照，携带 `_corrects_fetched_at` 指明被纠正的旧误标时间，原快照保留。清洗重放可以复现该纠正，不需要重新请求页面。

## 断点、原始资料与报告

每批输出到 `data/raw/zol-sync-<批次>/`：

- `html/`：响应 HTML 与 URL、状态、时间、编码等元数据。
- `phones.jsonl`：通过页面校验的原始产品记录，按完成顺序追加。
- `checkpoint.json`：已发现产品、完成页面、成功详情、发布进度与失败历史。
- `report.json`：该批次最终覆盖情况。

`data/reports/latest_sync.json` 供网页、CLI 和质量面板读取。主要字段：

| 字段 | 含义 |
| --- | --- |
| `listed_discovered` | 当前已发现的列表独立产品数 |
| `variants_discovered` | 系列额外发现的版本数 |
| `completed` | 通过校验的有效详情数 |
| `imported` | 已经自动清洗并发布的记录数 |
| `failed` / `unresolved_errors` | 尚未解决的 URL 或发布失败 |
| `failed_attempts` / `failure_history` | 历史失败事件，成功恢复后仍保留 |
| `warnings` | 已恢复失败或由另一正常公开布局补全的旧路由问题 |
| `list_totals_observed` / `list_count_mismatch` | 源站各页数量声明与实测独立数的差异 |
| `series_count_discrepancies` | 系列宣传数量与实际可见成员的差异 |
| `series_comparison_pages` | 成功解析的公开系列参数对比页数 |
| `brand_coverage` | 每个品牌主列表条数、新品模块条数、完成条数、零发现/未解决 ID 和来源 URL |
| `official_models_discovered` / `official_records_discovered` | 官方目录型号 URL 数与实际有效 SKU 行数，二者不能混算 |
| `official_pending` / `official_coverage` | 官方各品牌目录尚未采集的条目和限制；存在 pending 时报告 `partial` |
| `cross_source_gaps` | 两来源本批实际 family 差异，不能据此断言另一来源或市场没有该机型 |
| `status` | `running`、`complete` 或 `partial` |

成功详情逐条写入存储，一个产品清洗或写入失败不会回滚其他产品。HTTP 超时、429 和部分 5xx 最多尝试三次并有限退避；验证页不会反复重试。未解决的失败会明确列出原因，后续可接续恢复。

官方采集函数是 `phone_assistant.official_sources.sync_official()`，各品牌真实采集报告单独写到 `latest_official.json`。已采集并发布的官方报告可用 `merge_official_report(Path("实际报告路径"))` 离线合入同步报告，不再请求网站、不重复写库，原始响应时间保留；重复合入不会重复累计成功数。新库恢复可显式传 `import_records=True` 导入其中的原始记录。

## 验证

```powershell
uv run pytest tests/test_crawler.py -q
```

测试覆盖双布局、真实分页路径、系列跨页聚合、完整参数对比表及错位拒绝、停产证据、未知价格、验证页拒绝、参数身份、失败隔离、断点恢复、缓存来源时间、离线纠正和同步互斥。旧批次纠正不会覆盖后来真实采集的参数和价格，清洗重放也保持这一结果。测试不访问互联网或数据库服务，存储集成回归使用临时 SQLite 文件。实际覆盖结果以运行报告为准。

## 本次实际采集（2026-10-03）

批次 `2026-10-03T073916134760-0000` 完成正常公开列表、时间排序入口和系列扩展，取得 288 个列表独立产品与 427 个额外版本，共 715 条有效详情，全部已清洗发布，涉及 28 个源站品牌标签。保存了 10 个有效列表页面、210 个有效系列首页与 31 个系列参数对比页；全部发现的产品详情已经完成。31 个原本只显示四行的系列经参数对比页补齐后，所有已发现系列的宣传总数与独立型号数一致，`series_count_discrepancies` 为空。

结果仍为 `partial`：14 个列表分页 URL 曾返回源站访问验证，未绕过，其中三个旧列表路由由同筛选、同页码的正常网格页面补上，剩下 11 个未解决 URL（包括热门第四页两个布局的同一缺口）。各已采页面声明总数为 42、185、207、214、224、250、535、622，不能据此认定完整在售机型集合。时间排序的第一页及第四、第五页成功，第二、第三页被验证拦截。公开源仍展示旧机型、未售机型与停产系列版本，应用必须结合上市年份、在售状态与字段来源使用数据，不能把今天抓取当作今天上市。参数对比页也保留源站的参考价更新日期，今天读取不表示价格今天调整。

本批次的 HTML、真实响应时间、未解决 URL 和历史失败保存在原始目录与报告，旧的 4018 条历史 Excel 资料继续保留。这些缺口是报告的组成部分，后续正常源站响应恢复时可继续采集。

## 新品发现修复与真实补采（2026-10-04）

批次 `2026-10-03T172139810095-0000` 使用新品模式，实际 ZOL 明确新品模块发现 211 个独立 SKU，系列扩展后 241 条有效详情全部发布。五个目标品牌的模块均是 10 条发现、10 条完成，包含 X500、Find X10、Magic9、Mate90/nova16Pro、iPhone18Pro/ProMax等来源实际提供的机型；这些名称来自源页面，不是代码中的固定产品列表。

官方快照已发布 61 条 SKU，目录发现 267 个型号 URL。离线合入后整体报告为 302 条有效详情/302 条已发布，状态为 `partial`：16 个其他品牌 ZOL 目录返回验证；官方当前采集上限留下 226 个待采目录条目。源站一个新品模块通常只展示 10 个条目，不能宣称覆盖品牌全部新品。仍不把最近抓到的旧品牌“新品”标签当作今天上市，真实上市年月与未来状态由清洗层保留。

本批次离线恢复了 8 个另有同 SKU 确定报价来源的产品价格。其中 iPhone18Pro 2TB 为 20499、ProMax 2TB 为 21499，来自已采产品首页；其他“即将上市”SKU保持未知价格，不补造低价以进入预算推荐。官方完整报告与原响应另存于 `data/raw/official/reparsed_20261004/report.json`，原 HTTP 采集时间没有因重解析而修改。
